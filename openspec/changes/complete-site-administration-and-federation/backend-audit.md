# P4 backend contract audit

Checked against LemmyMultisite commit `1c9a50a90`. Paths below are relative to that repository. Recheck the running backend revision and database migration state before live acceptance.

| Area | v4 contract and authorization | Current tenant boundary and follow-up |
| --- | --- | --- |
| Site setup and settings | `POST /site` and `PUT /site` require a site administrator. `CreateSite` and `EditSite` are in `crates/db_views/site/src/api.rs`. | Backend commit `5f8d43d80` scopes rate-limit updates and bulk email-verification and registration-acceptance updates by local site ID. `crates/api/api/src/site/configuration_tenant_tests.rs` contains cross-site regression coverage. Live tenant isolation still needs acceptance against an isolated multi-site fixture. |
| Site icon and banner | `POST` and `DELETE /site/icon` and `/site/banner` require an administrator; uploads accept an image and return `image_url` and `filename`. | The handlers select the site via `TenantContext` and use site-scoped media references. They do not explicitly invalidate the cached site response after changing the site; verify freshness or fix invalidation before acceptance. See `crates/routes/src/images/{upload,delete,utils}.rs` and `crates/api/api_crud/src/site/read.rs`. |
| Registration applications | `/admin/registration_application/list` is cursor-paged and supports `unread_only`; `PUT /admin/registration_application/approve` takes `id`, `approve`, and optional `deny_reason`. Both require an administrator. | The list uses `tenant.local_site().id`. The approval transaction calls unscoped `RegistrationApplication::update` and `LocalUser::update` by ID, then reads the result for the authenticated site after the transaction. A cross-site ID can therefore mutate another tenant before the read fails. See `crates/api/api/src/site/registration_applications/approve.rs`. |
| Pending follows | `/community/pending_follows/list` accepts `unread_only`, `all_communities`, `page_cursor`, and `limit`; only admins can request all communities. `/community/pending_follows/approve` takes `community_id`, `follower_id`, and `approve`. | The list and action enforce moderator or administrator access. The list does not support a `community_id` filter. See `crates/api/api/src/community/pending_follows/` and `crates/db_views/community_follower_approval/src/api.rs`. |
| Taglines and emoji | `/admin/tagline` and `/custom_emoji` provide create, update, and delete; their list endpoints return cursor pages and a category-filtered collection respectively. Mutations require an administrator. | Both resources carry `local_site_id`, and mutations use site-scoped operations. See `crates/api/api_crud/src/tagline/` and `custom_emoji/`. |
| OAuth provider management | `/oauth_provider` supports administrator create, update, and delete. Provider lists are in `GET /site`; the admin list excludes the secret during serialization. Updates accept an optional secret and do not support changing issuer or client ID. | Provider reads and mutations use site ownership. See `crates/api/api_crud/src/oauth_provider/`, `site/read.rs`, and `crates/db_schema/src/source/oauth_provider.rs`. |
| OAuth sign-in | `/oauth/authenticate` takes code, provider ID, redirect URI, optional PKCE verifier, registration information, and TOTP. The backend checks the provider's site and exact callback URI. | `crates/api/api_crud/src/user/create.rs` returns a JWT in the response body but does not set an HttpOnly session cookie. The existing frontend session requires the cookie. Successful session restoration remains blocked on a backend contract change. |
| Instance policy and resolver | `/federated_instances` accepts `kind`, `domain_filter`, and cursor paging. `/admin/instance/allow` and `/block` take a domain and reason; block accepts optional Unix expiry. `/resolve_object` accepts `q`. | Federation policy queries use the tenant ID; resolver applies the current site's private-instance and object visibility rules. See `crates/api/api/src/site/federated_instances.rs`, `admin_allow_instance.rs`, `admin_block_instance.rs`, and `federation/resolve_object.rs`. |
| Users | `/admin/users` lists local users with `banned_only`, `sort`, and cursor paging. `POST /admin/add` takes `person_id` and `added`; the backend enforces the administrator hierarchy. | The list queries `tenant.local_site().id`, and role changes use `read_person_for_site` and `update_for_site`. See `crates/api/api/src/site/admin_list_users.rs` and `local_user/add_admin.rs`. |
| Media | `/image/list` returns a cursor page of `LocalImageView` rows for the administrator's site. `DELETE /image` takes `filename`. | `crates/routes/src/images/delete.rs` implements administrator deletion with `purge_image_from_pictrs`, which deletes aliases globally and does not check site ownership or shared references. Read-only inventory is implemented; do not expose this deletion until the backend supplies a site-safe contract. |
| Permanent purge | `/admin/purge/{person,community,post,comment}` accepts the corresponding target ID and a reason; the handlers require a site administrator and check target ownership. | Person purge schedules `purge_user_account`, which calls `Comment::permadelete_for_creator` and `Post::permadelete_for_creator` without a site filter. Community and post purge physically delete canonical rows, while migrations retain cascading foreign keys from post to community and comment to post. Verify cross-site descendants and references before exposing these actions. See `crates/api/api/src/site/purge/`, `crates/api/api_utils/src/utils.rs`, `crates/db_schema/src/impls/{comment,post,presence}.rs`, and migration `2022-07-07-182650_comment_ltrees/up.sql`. |
| Existing reports, modlog, bans, and votes | Reports use `/report/list` and type-specific resolve endpoints; modlog and user bans use `/modlog` and `/admin/ban`. Vote defaults use the site update contract. | Preserve the existing workspaces. Site-update isolation is covered by the backend fix above; use isolated fixtures for destructive moderation acceptance. |

The backend's current `ListCommunityPendingFollows` has no community-specific filter, although the existing community-management view sends `community_id`. The cross-community queue uses only supported fields. The community-specific view requires separate correction to avoid presenting unrelated rows as belonging to a single community.
